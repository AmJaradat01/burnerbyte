---
title: Single Sign-On (SSO)
description: OIDC-based SSO integration.
---

## Configuration

```yaml
sso:
  provider: https://accounts.google.com
  client_id: your-client-id
  client_secret: your-client-secret
  redirect_url: http://localhost:8080/api/v1/auth/sso/google/callback
  tenant_id: your-tenant-id
  issuer_url: https://accounts.google.com
  auto_provision: true
  default_org_role: member
  default_team_role: member
  allowed_domains: example.com,corp.example.com
```

## Flow

1. User clicks "Sign in with SSO" on the login page
2. Frontend redirects to `GET /auth/sso/{provider}`
3. Server generates a state cookie (600s TTL) and redirects to the OIDC provider
4. User authenticates with the provider
5. Provider redirects back to `GET /auth/sso/{provider}/callback`
6. Server validates the state, exchanges the code for tokens, and extracts user info
7. If the user exists, they're logged in. If not, a new account is created
8. Server redirects to the frontend with access and refresh tokens as query parameters

## Enforcing SSO

Org admins can enforce SSO for all members via org settings:

```bash
PUT /orgs/{orgId}/settings
{"enforce_sso": true}
```

When enforced, password-based login is disabled for org members.

## SSO Status

Check whether SSO is configured and available:

```bash
GET /auth/sso-status
```

Returns the current SSO configuration status (enabled/disabled, provider name) without exposing secrets.

## Admin SSO Management

Platform admins can view and update SSO configuration via the admin API:

```bash
GET /admin/sso
PUT /admin/sso
```

The `PUT` endpoint accepts the full SSO configuration object. Sensitive fields (client secret) are encrypted at rest using the configured `encryption.key`.
