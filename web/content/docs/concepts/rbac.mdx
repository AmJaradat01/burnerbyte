## Role Hierarchy

BurnerByte uses a two-level RBAC system with 3 org-level roles and 2 team-level roles. Roles and their permissions are stored in the database and can be managed via the admin API and Settings → Roles tab.

### Org Roles

| Role | Description |
|---|---|
| `owner` | Full control. Can delete org, manage billing, transfer ownership |
| `admin` | Can manage members, domains, teams, settings. Cannot delete org |
| `member` | Can view org resources. Access to teams they belong to |

### Team Roles

| Role | Description |
|---|---|
| `lead` | Full control of team settings, members, domain assignments, webhooks, API keys |
| `member` | Can create inboxes, view emails, manage own resources |

## Dynamic Role Management

Roles and permissions are stored in the `roles`, `permissions`, and `role_permissions` database tables. System admins can create, edit, and delete roles via:

- **UI**: Settings → Roles tab — full CRUD (create, edit, delete)
- **API**:
  - `POST /admin/roles` — create a new role with `{ name, label, description, scope, permissions: ["key1", "key2"] }`
  - `PATCH /admin/roles/{roleId}` — update label, description, or permissions
  - `DELETE /admin/roles/{roleId}` — remove a custom role

### Permission Keys

Org permissions: `org.settings.manage`, `org.delete`, `org.members.invite`, `org.members.remove`, `org.members.role`, `org.domains.manage`, `org.teams.manage`, `org.audit.view`, `org.view`

Team permissions: `team.settings.manage`, `team.members.manage`, `team.webhooks.manage`, `team.apikeys.manage`, `team.domains.manage`, `team.inboxes.manage`, `team.emails.view`

## System Admin

The `is_system_admin` flag on the user record grants access to all `/admin` routes including:
- System stats and health checks
- User management (list, edit, delete platform users)
- Platform settings (registration, email verification, password policy, lockout)
- SSO configuration
- Role and permission management

This flag is set during the initial setup wizard for the platform owner.

## Encryption at Rest

Sensitive configuration values (SSO client secrets, SMTP passwords) are encrypted with AES-256-GCM before storage in the `system_configs` database table. To enable, set the `encryption.key` config value to a 64-character hex string (32 bytes). Generate with: `openssl rand -hex 32`.
